# VN風 AIチャットアプリ 仕様書

## 1. 概要

### 1.1 コンセプト

本アプリは、ChatGPT等の一般的なAIチャットと同様の用途・会話体験を、**ビジュアルノベル／ギャルゲー風のUI**で提供するデスクトップAIクライアントである。

ストーリー生成、恋愛シミュレーション、好感度、ルート分岐等のゲームシステムを主目的とはしない。

AIには、日常的な質問、相談、文章作成、コーディング、調査、ファイルを用いた作業など、通常の汎用AIアシスタントと同様の用途で会話する。

初期実装では、まず通常のテキスト会話ができることを目指す。Web検索・ファイル添付・外部ツール実行はMVPの対象外とし、調査やファイル作業への対応は将来の拡張とする。

ゲーム的要素は主として**UI・演出・キャラクター表現**に用いる。

### 1.2 基本方針

- AIとしての実用性を損なわない
- 通常のチャットUIではなく、VNの操作体系へ置き換える
- キャラクターとの会話感を立ち絵・表情差分・文字送り等で強化する
- ストーリーや恋愛ゲーム固有のシステムは原則として持たない
- 1つの会話を永続的に続ける前提ではなく、ChatGPTのように複数セッションを作成する
- セッション管理等の一般的なAI UIも、可能な範囲でVNのメタファーへ変換する

---

## 2. 想定プラットフォーム・技術構成

### 2.1 プラットフォーム

デスクトップアプリとして提供する。

Webブラウザ上のサービスではなく、PC用ゲーム／デスクトップアプリとしての質感を重視する。

### 2.2 基本技術

初期実装では以下を使用する。

- Electron
- React
- TypeScript
- ローカルデータベース（SQLite）

追加ライブラリは必要に応じて選定する。APIキーは会話履歴と分離し、利用可能な場合はOSの暗号化機能で保管する。安全な保管機能がない環境ではメモリ内のみで保持する。

### 2.3 開発用診断

開発時はローカルの読み取り専用診断APIと診断ファイルから、通信・JSONL解析・保存・表示ページ・操作待ち状態を確認できるようにする。キャラクターについても、保存済み・現行セッション・編集中の情報を区別して取得する。

状態とイベントログでの診断を優先し、スクリーンショットは必要時のみ取得する。診断データは配布アプリでは提供せず、Git対象外とする。詳細は [診断ガイド](diagnostics.md) を参照する。

## 3. 基本画面

メイン画面は一般的なPC向けビジュアルノベルを基本とする。

主な構成要素：

- 背景
- キャラクター立ち絵
- キャラクター名
- メッセージウィンドウ
- ページ送り表示
- ユーザー入力UI
- BACKLOG
- PHONE
- SETTINGS等の補助UI

概念イメージ：

```text

│                 背景                       │
│                                            │
```

ブラウザ的なサイドバーやメッセージバブルの縦積み表示は、メインUIでは使用しない。

## 4. AI応答表示

### 4.1 基本表示

AIの返答はVNのメッセージウィンドウ内に表示する。

一度に画面へ収まらない場合、通常のVNと同様にページ単位で表示する。

続きがある場合は `▼` 等を表示し、ユーザーがクリックまたは対応キーを押すことで次の文章へ進む。

AIの応答は台詞（`speech`）と地の文（`narration`）を区別する。地の文のページではキャラクター名の欄を表示しない。地の文では直前の表情を維持し、必要な場合のみ描写を生成する。通常の質問への回答・説明を地の文に置き換えない。

最初の挨拶は、引用符付きの台詞がある場合に台詞とその前後の地の文へ分ける。引用符のない挨拶は台詞として扱う。既存セッションの挨拶も、履歴を書き換えず表示時に区別する。台詞を囲む外側の引用符はメッセージウィンドウへの表示時に外し、内部の引用と元の文章は保持する。

### 4.2 Streaming

**LLMのStreaming応答は必須とする。**

全回答生成完了まで待ってから表示する方式にはしない。

LLMの出力形式はJSONL（1行につき1つのJSONオブジェクト）とする。完全なJSONオブジェクトを受信し、解析・検証に成功した時点で、その発話セグメントを表示キューへ追加する。回答全体の生成完了は待たない。

未完成の行やJSON文字列の内部を部分解析して表示する必要はない。分解できない1セグメントは、そのオブジェクトの受信完了まで待ってよい。通信チャンクと行境界は一致しないため、未完成の行はバッファへ保持する。モデルが区切りの改行を省略した場合も、文字列内の括弧・引用符・エスケープと入れ子を区別し、完成したJSONオブジェクトごとに即座に処理する。未完成のJSONを補完したり、配列から内部のオブジェクトを抽出したりはしない。

LLMのトークン受信速度と画面上の文字送り速度は、必要に応じて分離できる設計とする。

現在表示中の文章の即時表示と、回答生成の停止操作を提供する。1行が長い場合に表示開始まで待ち時間が生じることは許容する。

不正なJSONL行はスキップして通知・記録し、正常に受信済みの内容は保持する。停止・通信切断では未完成行を破棄し、回答を中断またはエラーとして保存する。未定義の表情IDはデフォルト表情へ戻す。

### 4.3 発話セグメント

AI回答は必要に応じて複数の発話セグメントへ分割する。

概念上のデータ：

```ts
type Segment = {
  type: "speech";
  expression: string;
  text: string;
};
```

例（各行が独立したJSON）：

```jsonl
{"type":"speech","expression":"face_02","text":"うーん、その方法でもできますが、一つ問題があります。"}
{"type":"speech","expression":"face_05","text":"……あ、待って。もっと簡単な方法があります。"}
{"type":"speech","expression":"face_03","text":"これならかなり綺麗にできますよ。"}
```

`text` 内の改行はJSONのエスケープ表現 `\n` とし、1オブジェクトを複数行へ整形しない。

地の文は次のJSONL形式とし、表情IDは不要とする。

```jsonl
{"type":"narration","text":"彼女は少し考えてから、頷いた。"}
```

台詞と地の文は別ページに分ける。セグメント切替に応じて表情も変更できる。

同一セグメントが長い場合は、UI側でさらに複数ページへ分割してよい。ウィンドウやフォントのサイズ変更でも文章が欠落しないよう、実際の表示領域に合わせてページ分割する。

## 5. 表情差分システム

### 5.1 基本思想

アプリ側では表情の種類を固定しない。

`happy`、`sad`、`angry` 等の固定enumは設けない。

利用可能な表情は**キャラクターごとに自由に定義**する。

### 5.2 表情定義

各表情は最低限以下を持つ。

```json
{
  "id": "face_03",
  "image": "face_03.png",
  "description": "嬉しい、楽しい、相手に好意的なときに使う表情"
}
```

`description` はLLMが表情を選択するための自然言語説明である。

例：

```text
face_01
通常。特に強い感情がないとき。

face_02
考え込んでいる、判断に迷っているとき。

face_03
嬉しい、楽しい、相手に好意的なとき。

face_04
呆れている、疑っている、軽く非難するとき。
```

### 5.3 LLMによる表情選択

LLMには現在利用可能な表情IDと説明を提示し、生成する発話に最も適したものを選択させる。

アプリは表情の意味を解釈せず、返されたIDに対応する画像を表示する。

これによりキャラクター作者は、任意の粒度・意味の表情差分を設定できる。

### 5.4 動的な表情変更

一回答につき一表情ではなく、**回答途中で表情を動的に変更できる**。

例えば、

```text
[考え顔]
「うーん、それは少し難しいですね……」

↓

[驚き]
「……あ、待って。」

↓

[笑顔]
「分かりました。これならできますよ。」
```

のように表示する。

LLMには、不必要に頻繁な表情変更を行わず、自然な発話・感情単位でセグメントを分割させる。

表情変更時のクロスフェード等の細かな演出は実装時に調整する。

## 6. ユーザー入力

### 6.1 基本入力

ユーザーは通常のテキスト入力欄から自由入力する。

入力が長くなった場合、入力ウィンドウ内部でスクロール可能とする。

日本語IMEの変換確定Enterでは送信しない。Enterで送信、Shift + Enterで改行する。

### 6.2 「選択肢」としての送信演出

自由入力した文章を、そのまま通常のチャットメッセージとして送信するのではなく、**VNの選択肢として確定・選択したように演出する。**

想定フロー：

1. ユーザーが文章を入力
2. Enter等で確定
3. 入力欄がVNの選択肢風UIへ変化
4. 選択肢が押下されたように縮小・拡大
5. 決定SEを再生
6. ハイライト等の短いフィードバック
7. LLMへ送信
8. 選択肢UIを消去
9. AI応答待ち状態へ移行

例：

```text
入力中：

┌────────────────────────────┐
│ Electronで作ろうと思ってる │
└────────────────────────────┘

       ↓ Enter

選択肢：

╭────────────────────────────╮
│ ▶ Electronで作ろうと思ってる│
╰────────────────────────────╯

       ↓ 押下演出 + SE

LLMへ送信
```

自由入力でありながら「自分で選択肢を作り、その選択肢を選ぶ」という操作感を実現する。

### 6.3 添付ファイル（MVP対象外）

初期実装ではファイル添付を提供しない。以下は将来の拡張案とする。

入力欄付近に添付アイコンを設ける。

添付ファイル自体の選択UIは一般的なものでもよいが、メイン画面の雰囲気を壊さないアイコン表現とする。

---

## 7. Thinking・処理状態

LLMやシステムの処理状態として `Thinking...` 等を表示してよい。

これらを完全にゲーム世界内の演出へ変換する必要はない。

例：

- Thinking...
- Searching...
- Reading file...
- Generating...

MVPでは通常会話の生成状態のみを扱う。`Searching...` や `Reading file...` は、将来それぞれの機能を実装した場合の例であり、実際に行っていない処理は表示しない。

必要に応じて立ち絵の表情と併用する。

演出を過剰に増やすことは初期優先事項としない。

---

## 8. ファイル・成果物表示 ― PHONE

### 8.1 コンセプト

コード、Markdown、PDF、画像、生成ファイル等をメッセージウィンドウ内へ無理に表示しない。

これらは**「キャラクターがユーザーのスマホへ送信した」**というUI上の設定で扱う。

### 8.2 PHONE UI

メイン画面に `PHONE` またはスマートフォンアイコンを配置する。

新しいファイル等を受信した場合は通知バッジを表示できる。

PHONEを使う回答では、「資料をスマホに送ったよ。PHONEから見てね」「詳しい説明をスマホに送るね」など、送る内容とスマホで読めることをキャラクターの発話で明示する。「こちらです」だけの曖昧な案内にはしない。案内のspeechは対象のphone行の直前に出力する。実ファイル生成を伴わない場合は、ファイルを作成・添付したとは言わず、実際にPHONEへ表示する説明やコードを案内する。

例：

```text
┌────── PHONE ──────┐
│                   │
│ Alice             │
│ ───────────────── │
│ 📄 summary.pdf    │
│ 🖼 diagram.png    │
│ 📝 sample.ts      │
│ 🔗 Reference URL  │
│                   │
└───────────────────┘
```

### 8.3 初期実装

PHONEは初期段階から実装する。外観は開閉できるシンプルなパネルでよく、スマートフォンの精密な再現や複雑な演出は不要とする。

コード、Markdown、長文の詳細など、VNのメッセージウィンドウでは読みにくい内容はこちらへ表示する。初期パネルはスクロール、テキスト選択・コピー、およびコードの改行・インデント維持に対応する。

この段階では、PDF・画像等の専用ビューアや、実ファイルの生成・添付・Web検索は必要としない。VN上の発話とPHONE表示は、JSONLの `type` で区別する方式を初期案とする。例：

```jsonl
{"type":"speech","expression":"face_02","text":"コードをスマホに送るね。PHONEから見てね。"}
{"type":"phone","format":"code","language":"typescript","text":"const value = 1;"}
```

発話セグメントにも `type: "speech"` を付ける。PHONE用の `format` はコード・Markdown・プレーンテキスト等を識別する。詳細なフィールドや振り分け方は、実際に使いながら改修する。

### 8.4 将来の対応対象

将来、PHONEから閲覧する対象として以下を想定する。

- PDF
- テキストファイル
- Markdown
- ソースコード
- 画像
- AI生成ファイル
- URL / Web検索結果
- その他添付物

PHONE内部は実用性を優先し、通常のアプリケーションUIに近くてもよい。

## 9. BACKLOG

### 9.1 基本機能

過去の会話はチャットログではなく**BACKLOG**として表示する。

AIとユーザー双方の発言を時系列で確認できる。

例：

```text
BACKLOG

Alice
「Electronならかなり相性いいと思うよ」

YOU
「Reactで作ろうと思ってる」

Alice
「だったら……」
```

### 9.2 過去プロンプト編集

ユーザーの過去発言はBACKLOGから編集可能とする。

編集した場合は、その地点から会話を再生成できるようにする。

編集を確定した場合、編集中の会話ではその発言を置き換え、それより後の発言・回答を破棄して再生成する。以前の会話への復帰や分岐履歴の保持は不要とする。

編集した発言以降の履歴には戻れない。他のセッションの履歴には影響しない。

通常の会話画面には編集ボタン等を常設せず、BACKLOG側へ集約する。

## 10. キャラクターカード

### 10.1 SillyTavern互換

キャラクター定義は、可能な限り**SillyTavernで利用されているCharacter Card形式との互換性を持たせる。**

既存Character Cardのimportを可能にすることを想定する。

### 10.2 独自拡張

表情差分等、本アプリ固有の情報は独自仕様となる。

Character Cardそのものを破壊的に変更するのではなく、内部で拡張情報と統合して扱う方向とする。

概念：

```text
SillyTavern Character Card
        │
        ├─ name
        ├─ description
        ├─ personality
        ├─ scenario
        ├─ first_mes
        └─ ...
             │
             ▼
      Character Runtime
             +
       VN Extension
        ├─ expression sprites
        ├─ expression descriptions
        ├─ default expression
        └─ その他UI情報
```

初期実装ではCharacter Card V1/V2（2.0）のJSON、および `chara` のtEXtチャンクを持つPNGに対応する。解析はローカルで行い、LLMは使用しない。名前・説明・性格・状況・会話例・最初の挨拶を取り込み、PNG画像を最初の表情画像として利用できる。未対応のプロンプト上書き・Lorebook・代替挨拶・拡張情報は、未知の項目とともに元データとして保持し、未対応であることを画面に示す。

インポート時の元JSONは編集用の設定とは別に保持し、設定の編集では書き換えない。元の各フィールドを個別に取り込み、説明欄の文章を性格等の別項目へ自動再分類しない。PNGファイルそのものの原本保存とは区別する。

### 10.3 キャラクター管理

CHARACTER画面で新規作成・編集・削除・カード読み込みを行う。名前、説明・口調、最初の挨拶、性格・状況・会話例、任意の表情ID・説明・画像、デフォルト表情を設定できる。

最初の挨拶は、セッション作成時にLLMを呼ばず発話として保存・表示する。空欄も許容する。

NEW SESSIONは現在のキャラクターで1クリックで開始し、選択画面を毎回挟まない。別キャラクターで開始したい場合は、CHARACTERで選択して新規セッションを作成する。

### 10.4 立ち絵・標準背景

ユーザーが用意したPNG/JPEG画像を登録する。全身・上半身の画像を区別して固定せず、共通プレビュー上で大きさ・左右位置・上下位置を調整する。表情差分間では同じ配置を使用する。

キャラクターごとに標準背景を登録できる。画像はアプリ内へコピーし、設定変更や画像差し替えによって既存セッションの素材が変わらないよう、変更しない画像ファイルを参照する。

同梱プリセットは仮素材とし、正式なキャラクター設定・画像はユーザーが用意する。

## 11. セッション管理 / SESSION

### 11.1 基本方針

用途ごとに独立した会話セッションを作成する。手動のSAVE / LOADは廃止し、左端のSESSIONから一覧を開く。

### 11.2 新規作成と自動保存

NEW SESSIONは現在のキャラクターの最新設定で新しい会話を即座に開始する。挨拶は生成を待たずに表示する。この時点ではメモリ内の下書きとし、一覧・データベースには保存しない。

最初のユーザー入力を受け付けた時点で、挨拶・キャラクター設定・入力をまとめて保存し、一覧に追加する。タイトルは最初の入力から自動生成する。API設定不足等で入力を受け付けられない場合は一覧に追加しない。

以後はユーザー発言と、解析・検証が完了したJSONL行を逐次自動保存する。通信失敗でも受信済みの内容を残し、受信途中の行は保存しない。未送信の下書きは別セッションへの切替・終了で破棄する。

### 11.3 一覧からの再開

一覧にはタイトル・更新日時・キャラクター画像を表示し、選択してその会話を再開する。名前変更・削除も一覧内で行う。切替時は進行中の生成を停止する。新たな履歴コピーは作成しない。

起動時は最後に選択した保存済みセッションを復元する。保存済みセッションがない場合は新規下書きを開く。異常終了時の生成中回答は中断として扱う。

旧版のSAVEで作られた履歴コピーも通常のセッションとして保持し、再開できる。

### 11.4 CharacterとSessionの分離

同じキャラクターで複数の独立した会話を作成できる。各セッションは作成時の設定・画像参照・背景・配置を保持し、ライブラリの変更で既存の会話を変えない。

## 12. ナビゲーション

`mock/` のレイアウトを基準にする。会話画面には左端のSESSION、右上のCONFIG、右側のPHONE、メッセージウィンドウに付随するLOGを配置する。

- SESSIONは左ドロワーで一覧とNEW SESSIONを表示する。同じキャラでの新規開始は左端の＋、または⌘/Ctrl+Nでも行える。
- CONFIGから専用の設定画面を開く。サイドバーで設定とキャラクター管理を切り替え、会話に戻れる。
- キャラクター管理はカード一覧と詳細編集に分け、詳細では立ち絵プレビュー・配置調整・各表情の設定を行う。
- PHONEとBACKLOGは会話画面上のオーバーレイとする。PHONEは種類別一覧から各内容を開く。

## 13. LLM接続

本アプリは特定LLMへの依存を避ける方向とする。

将来的には以下のような複数Providerへの対応を想定できる。

- OpenAI
- Anthropic
- Google Gemini
- OpenAI互換API
- OpenRouter
- ローカルLLM / Ollama等

テスト段階の接続先はOpenRouterとする。まずはOpenRouter経由の通常のテキスト会話とStreamingに対応する。使用モデルは設定で指定し、JSONL出力の安定性を確認する。

Provider抽象化の概念例：

```ts
interface LLMProvider {
  chat(
    messages: Message[],
    options?: ChatOptions
  ): AsyncIterable<LLMEvent>;
}
```

Streamingを前提としたAPI設計とする。

## 16. MVP案

最初の実装では以下に絞る。

1. Electronデスクトップアプリ
2. OpenRouter接続（テスト段階）
3. Streaming会話
4. VN形式のメッセージウィンドウ
5. クリックによるページ送り
6. 自由入力
7. 入力確定時の「選択肢押下」演出＋SE
8. キャラクター立ち絵
9. 任意定義の表情差分
10. LLMによる表情選択
11. 回答途中での動的表情変更
12. BACKLOG
13. セッションの自動保存
14. 最初の入力でのセッション保存、SESSION一覧からの再開・名前変更・削除
15. SillyTavern Character Card importの基礎対応
16. コード・Markdown・長文の詳細を表示するシンプルなPHONEパネル（初期段階から実装）

通常会話の基盤に続き、キャラクター管理UI・Character Card V1/V2 import・ユーザー画像登録・標準背景・配置プレビューを実装する。既存セッションは作成時のキャラクター設定と素材参照を保持する。

MVPでは通常のテキスト会話を成立させることを優先する。Web検索、ファイル添付、外部ツール実行、PDF・画像等の専用ビューア、高度なProvider切替等はMVP後とする。

## 17. プロダクトの核

本アプリの目的は「AIキャラクターゲーム」を作ることではない。

**汎用AIとの通常の会話を、ビジュアルノベルのUI・操作感・キャラクター表現で体験できるデスクトップクライアントを作ること**を目的とする。

そのため、機能追加時には常に以下を基準とする。

> この機能はAIとして便利になるか。
>
> その便利さを損なわず、VNの文法で自然に表現できるか。

ゲーム性そのものを増やすことは目的としない。
